The files of the stack

This page lists each file that the stack reads or writes, the meaning of each key in it, and how the files work together. How the stack fits together tells what an install does, and this page gives the files behind it.

The examples come from an install into an empty Python project on 2026-10-31, with the command just install --profile python --defaults.

Terms

Term Meaning
package A Git repository that ships skills, for example nossaifd.
clone The local Git clone of a package. The installer reads each package from its clone.
role The name of a job, for example tasker. One package does the job.
profile A language setup, for example python. A profile package, such as jnprofile-python, ships it.
tool One unit of a profile, for example lint. It brings packages, recipes and parts.
owner A thing that adds to the files of a project: jnterfaces, a profile, a tool, or a role. A tool has the key profile:tool, for example python:lint.
shared file A file that more than one owner, and you, can add to, for example .gitignore or pyproject.toml.
part What one owner adds to one shared file.
unit The smallest piece of a part: one line, one key, one list item or one hook.
record A JSON file in .agents/ that says what the installer wrote.
own file A file that the installer writes whole under .agents/, for example .agents/config/python/ruff.toml or .agents/instructions/tasker.md. A shared file includes it or points to it.

One record for each project

A project has one record of the stack, .agents/stack.json. A profile or a role does not bring a record of its own. Each run of the installer reads what the packages declare, and writes all of it into this one file.

Two other names can confuse you:

  • stack.json at the top of jnterfaces is the catalog. It lists the packages, roles and profiles. It is not in your project.
  • .agents/<package>-install.json is one file for each package. It keeps the hashes of the skill files that the package copied in. It does not hold the shared files.

The files at a glance

Each package declares what it installs. The installer reads the declarations, then writes the project and its records.

File Where Who writes it What it holds
stack.json jnterfaces the author of jnterfaces The catalog: each package, role and profile.
scripts/formats.json jnterfaces the author of jnterfaces The format of each shared file that a part can go to.
skill-package.json each package the author of the package The skills and the extras of the package.
profile.json each profile package the author of the profile The tools of the profile, and the parts of each tool.
.agents/stack.json the project the installer The record of the stack: your choices and each part.
.agents/<package>-install.json the project the installer The record of one package: its revision and the hash of each of its files.
.agents/stack-pending.json the project the installer The state of a run that has not finished. It is gone after a run that works.
.agents/stack-log.jsonl the project the installer A history of the runs. Nothing reads it to decide what to do.
.agents/just/index.just and .agents/just/<profile>.just the project the installer The modules that import the recipes of the installed tools. generated in the record keeps their hashes.
.agents/just/<profile>/*.just and .agents/just/roles/<package>.just the project the packages, through install_extras.files The recipe files of each tool and role. The package record keeps their hashes.
.agents/config/<profile>/... the project the installer The own files of the tools.
.agents/instructions/<role>.md the project the installer The own file of a role. A line in AGENTS.md points to it.
.agents/install.just the project the installer The recipes just install and just uninstall.
.agents/log/ the project jlog The run log of the recipes. Git ignores it, and no owner of a part may name it.
.agents/skills/ and .claude/skills/ the project the installer The skills, and a link to each one for Claude Code.
.claude/hooks/ and .codex/hooks/ the project the tasker role, through install_extras.files The hook scripts. The hook entries go in .claude/settings.json and .codex/hooks.json as parts.
.agents/generated.txt and .agents/coverage-exclude.txt the project the installer once, then you Two empty lists, in a project that the installer starts. You or an agent add paths, and test-review of the tasker role judges each one. A list that you delete stays deleted.
Justfile the project the installer once, then you The starter Justfile, when the project has none. It is yours from then on. In a Justfile of your own, the installer adds one block with the line import? '.agents/install.just'.
CLAUDE.md the project the installer once, then you The line @AGENTS.md, when the project has AGENTS.md and no CLAUDE.md. Claude Code reads CLAUDE.md and not AGENTS.md, and the line imports AGENTS.md. It is yours from then on.
.gitignore, .worktreedisposable, AGENTS.md the project the installer and you Line files. Each owner adds a block of lines.

How one run uses the files

  1. just install runs scripts/install_stack.py from the jnterfaces clone.
  2. The installer reads the catalog stack.json. It finds each role, profile and alias there.
  3. It reads .agents/stack.json of the project for your saved choices. Names on the command line change them.
  4. For each package that the run needs, it reads skill-package.json from the clone. For each profile, it also reads profile.json.
  5. It makes one owner from each profile, tool and role, with its lines, parts and units. scripts/formats.json tells it how to read and write each shared file. It does a dry pass over the shared files. A conflict of two owners stops the run here, before anything changes.
  6. It copies the skills and the extra files of each package. It writes .agents/<package>-install.json for each one.
  7. It saves your choices in .agents/stack.json, and writes the modules in .agents/just. It does this again each time that it saves the record.
  8. If the project has no Justfile, it writes the starter Justfile. If a tool needs the manifest and the project has none, it runs init of the profile.
  9. It runs the package commands of the tools, such as uv add --group lint ruff.
  10. It saves .agents/stack-pending.json, then it writes the shared files and the own files, and adds an entry to .agents/stack-log.jsonl. A Justfile of your own is a line file here, and it gets the block with the import of .agents/install.just. If the Justfile then does not parse, the installer takes the block out again.
  11. If the project now has AGENTS.md and no CLAUDE.md, it writes a CLAUDE.md with the line @AGENTS.md. If your CLAUDE.md does not import AGENTS.md, it says so and leaves the file alone.
  12. It saves the new parts in .agents/stack.json, and deletes .agents/stack-pending.json.

A removal, such as just uninstall lint, runs the same steps. The owner is not active, so its parts go. The installer reads what to take out from the record, never from the files.

In the packages

The catalog: stack.json of jnterfaces

The catalog has four keys:

Key What it holds
version The version of the format. It is 2 now.
packages A list with one entry for each package. jnterfaces is first.
aliases Other names for a role, for example "gest": "tasker".
profiles One entry for each profile, keyed by its name.

An entry of packages has these keys:

Key What it means
name The name of the package and of its clone folder.
repository The URL to clone when the clone is missing.
about One line for the questions and the help.
choice The role that the package does, for example tasker. jnterfaces has none, because it is always installed.
default true when a new project turns the role on, unless the profile says otherwise.
needs The packages that the role needs.
record The path of the package record, when it is not .agents/<package>-install.json.
drop_with The starter files that the role leaves out while another role is on, keyed by that role: files, and why, which the installer prints. The installer removes such a file when it wrote the file and you did not change it, and does not write it again while the other role is on. prose leaves out .github/workflows/nossaifd-prose.yml while tasker is on.
variants and default_variant The forms of a role, for example git or gitwt for tasker. A variant with "ready": false cannot be chosen yet.
required_skills and optional_skills For jnterfaces only: the just skill is always installed. cx and jagt-protocol are roles of their own.

An entry of profiles has package, repository, about, and detect. detect lists the files that turn the profile on in a project with no saved profile, for example pyproject.toml or uv.lock.

A package: skill-package.json

Each package has one skill-package.json. The installer reads these keys:

Key What it means
repository The owner, name and URL of the package.
skills Each skill, with its name and its folder.
install_extras.files Files and folders outside .agents/skills that the installer copies and records like a skill, for example .agents/just/roles/nossaifd.just.
install_extras.parts The parts of a role: {shared file: source file}. For example, tasker adds a line to AGENTS.md and hooks to .claude/settings.json.
install_extras.starter A file that the role writes once, when the project has none, for example the first AGENTS.md. It is yours from then on.
install_extras.programs The programs of a role, with the keys of the programs of a profile. A role that is on needs all of them. For example, tasker installs pre-commit, then its git hooks.
install_extras.before_remove {git_hook, command}. When the role goes and the Git hook is there, the command runs in the project before the files of the role go. For example, tasker runs pre-commit uninstall, because a hook without its config stops each commit. A failed command does not stop the removal.
install_extras.merge_hooks and install_extras.seed The same hooks and starter for an installer from before the parts. A newer installer leaves these files to the parts.
executables The tools table: the programs that the package needs, with a command that checks each one. Each entry of required can have the key install, the line that installs it, and the keys version and expect of a program of a profile. When the check of a required program fails, the installer stops before it writes anything, and prints the install line of the program, or else its description. An entry without a check needs its program on the PATH only. The installer never runs this install line. An entry of optional with the key skill counts as required while that skill is on, for example jagt for the jagt-protocol skill. The value of skill must be the name of a choice of the role, and the name of the skill is the same.
requires The versions of other packages that the package needs: {"jnterfaces": ">=0.1.0"}. The version of a package is its source_version, from its clone. Before it writes anything, the installer stops when a named package is not in the run, when its clone has no tag, or when its version is below the floor.

A profile: profile.json

A profile package also has profile.json. Its top keys are these:

Key What it means
version The version of the format. It is 1 now.
name, about, detect As in the catalog.
manifest The file that lists the dependencies: pyproject.toml, package.json or Cargo.toml.
init The manifest file and the command that makes it when it is missing: {"file": "pyproject.toml", "command": ["uv", "init", "--bare", "--no-workspace"]}.
add and remove The commands that add or remove the packages of a tool. {group} takes the group of the tool.
choices The default roles of the profile, for example tasker and prose.
uv_default_groups For Python: the value of tool.uv.default-groups in pyproject.toml.
base What the profile adds with no tool: its recipe file, its programs, and its lines, parts and files, as for a tool.
programs The programs that the profile can need, such as rustup. The next section tells the keys.
tools Each tool, keyed by its name.
default_tools The tools that a new project gets, for example lint and test.

A tool has these keys:

Key What it means
packages The packages that the tool adds, for example ruff.
group For Python: the dependency group of the packages.
recipes The recipe file of the tool, for example lint.just.
verify The recipes that just verify runs for the tool.
lines Lines for line files: {".gitignore": [".ruff_cache/"]}.
parts Parts for unit files: {"ruff.toml": "files/ruff.toml"}.
files Whole files, for an installer from before the parts. A file that is also in parts goes as a part.
skip_if A guard [file, text], or a list of guards. A new part is left out when any guard applies: the file has the text, for example no ruff.toml part when pyproject.toml has [tool.ruff. An empty text means that the file is there. In a TOML file, [a.b means that the table is there, and [a.b] means that the table holds a setting of its own, not only tables. A part that the record already holds stays.
before_remove A command that runs before its package goes, for example pre-commit uninstall. The package goes when the tool goes, or when no tool in that place lists it any more.
programs The names of the programs that the tool needs, from the top key programs.

The programs of a profile

A program is a command on the machine, such as rustup or cargo-llvm-cov. The top key programs is a list of programs. Each program has these keys:

Key What it means
name The name of the program. base.programs and programs of a tool use this name.
check A command that exits with 0 when the program is there, for example cargo llvm-cov --version.
expect Optional. A text that the output of check must have, for example llvm-tools.
version Optional. The version floor, >=X.Y.Z or >=X.Y, for example >=1.50.0. Without it, the check must pass, and any version counts.
install The command that installs the program, for example cargo +stable install --locked cargo-llvm-cov@0.9.1.
install_in Optional, with install. project, the default, runs install in the folder of the project. home runs it in your home folder, or in an empty folder outside the project when HOME is not set.
each_clone Optional, true, with install. The program is a setup of each clone, such as the git hooks of a role. See A setup of each clone.
description For a program without install: what a person does to get it. For a program with install: optional, what the program does.

A program needs install or description. The first word of check and of install is a program on PATH, not a path. The installer splits check and install into words, as a shell does. Then it runs them without a shell. So a command has no pipe, no $VARIABLE and no &&. The installer never downloads a script.

The base of a profile names the programs that it always needs, in base.programs. A tool names the programs that only it needs, in its own programs. A program of a tool that is off is not needed. The programs that a run needs are those of the base and of each installed tool, in the order of the top key programs. When two profiles have a program with the same name, the program of the first profile counts.

A role names its programs in install_extras.programs of its skill-package.json. They have the same keys and rules. A run needs each program of a role that is on, after the programs of the profiles. When a profile has a program with the same name, the program of the profile counts.

The version of a program is the first X.Y.Z, or X.Y, anywhere in the output of its check. The search covers the whole output, because some programs, such as gest, print a banner before the version. When the output has no version, the search goes on in the error output. The parts compare as numbers, so 2.101.0 is higher than 2.40. A check with a floor fails when the program is not on the PATH, when the check fails, when the output has no version, or when the version is below the floor. The message names the floor, the version found, the path of the program and the owner.

One floor for each program. The programs of the profiles and their tools, of the project, of the roles, and of the tools tables of the packages and their skills can name the same program. The installer joins them in this order, and the highest floor counts. The first entry gives the check, but an entry with install comes before an entry without one. The record keeps the floor of each owner. A floor that a tools table adds to a program with install is checked at the end of the run, when the installer checks that program again.

Owner Floors
jnterfaces, in each project jlog >=0.2.0, just >=1.50.0, uv >=0.12.13, git >=2.40, gh >=2.40
the jagt-protocol skill jagt >=0.3.0
the cx skill cx >=0.1.0
the tasker role gest >=0.6.0 and jagt >=0.6.3, when agent_gest_git_skills gives it

The checks run through jlog. When jlog 0.2.0 or later is on the PATH, the installer runs each check and each install of a program as jlog run COMMAND, from the folder of the command. So a check sees the PATH that a recipe line sees, also a tool that only .jlog/bin of the project gives. Without jlog 0.2.0, the installer uses its own PATH, and it says so once. The commands of the tools, such as uv add, keep the PATH of the installer. No command gets the VIRTUAL_ENV of the installer.

A check never installs or downloads. A check must only read. It must not install a program, download a file, or change the project. The installer sets RUSTUP_AUTO_INSTALL=0 and UV_PYTHON_DOWNLOADS=never for each check, so that rustup installs no toolchain that the project pins, and uv downloads no Python. The installer cannot stop every download, for example of uvx or npx, so do not start a check with them. Give such a program an install, and a check that only reads.

A run uses the programs in this order:

  1. Before it writes anything, the installer runs the check of each needed program without install. If a check fails, the installer prints the description and stops. It also stops for a missing program whose install starts with a command that is not on PATH. A command counts as on PATH when an earlier program with that name installs in the same run, because its check fails. The programs of the profiles come before the programs of the roles.
  2. It runs the commands of the tools, such as cargo add --dev. Then it writes the files, also the whole files of the base and the tools.
  3. In the folder of the project, it runs the check of each needed program with install. If a check fails, it runs install in the folder that install_in names, and then check again. If the check fails again, the run stops with an error.

These rules follow from the order:

  • The toolchain file counts. The checks of step 3 run in the project, so rustup reads the toolchain file of the project, if it has one.
  • install_in picks the toolchain of an install. rustup component add clippy runs in the project, so the component goes on the toolchain of the project. The rust profile runs cargo +stable install --locked cargo-llvm-cov@0.9.1 with "install_in": "home". In the home folder, the toolchain file of the project does not count, and an old toolchain that the project pins cannot fail the build. +stable picks the stable toolchain, also when rustup has no default toolchain. The program stable of the profile installs that toolchain first.
  • A command of a tool comes first. It runs before step 3, so it can use only programs without install.
  • A missing program stops a removal too. A missing program without install stops every run of its profile, also a run that only removes a tool.
  • A check that hangs fails. A check that takes more than 15 minutes fails. A check of cargo in a project with a toolchain that is not installed fails at once, and the program toolchain then installs it.
  • A dry run installs nothing. just install --dry-run prints each missing program and each install that it would run.
  • just install --check lists the missing programs. It fails when one is missing or below its floor. It reads the key programs of the record, so it also checks a project without the clones of its packages. It skips the rest of a profile or a role that has no clone. It changes nothing in the project.
  • A program stays. The installer never uninstalls a program, also when a tool, a profile or a role goes. The before_remove step of a role can take out what its programs put in the project, such as a Git hook.

A setup of each clone

Some programs are not on the machine, but in one clone of the project. An example is the git hooks of the tasker role. A fresh clone has no git hooks, so its commits skip the commit gate. Give such a program "each_clone": true.

  • just install sets it up. In each clone, just install runs the check, and runs install when the check fails. When the check passes, the run changes nothing.
  • The record keeps it. The key programs of .agents/stack.json has the program, with "each_clone": true. So tools-check, the first step of just check, runs its check in each clone. A clone without the setup fails just check, and the message says to run just install.
  • CI skips it. tools-check and just install --check do not run its check when the variable CI is set and is not 0 or false. CI makes no commits, so it needs no git hooks. GitHub Actions and GitLab set CI. On a runner that does not set it, such as Jenkins, set CI=true yourself.
  • A failed check says why. tools-check prints the last lines of the error output of the check. For example, the check of the tasker role names a .pre-commit-config.yaml without the hooks of the role.
  • The check decides the rest. For example, the check of the tasker role passes in a folder that is not a Git repository. Such a folder has no hooks to set up.

The programs of jnterfaces itself, git, gh, just, uv and jlog, are not in a profile. They are in executables.required of the skill-package.json of jnterfaces.

A toolchain file

A profile could write a toolchain file with the files of its base. A whole file is written only when the project has none. The rust profile writes no toolchain file. It keeps the rust-toolchain.toml or rust-toolchain of the project, and it names the toolchain as a program:

  • toolchain has the check rustup show active-toolchain and the install rustup toolchain install. Both run in the project, so the install gets the toolchain that the project pins. rustup 1.28.0 does not install a missing toolchain by itself, and later versions do.
  • Each component, such as clippy, is a program with the install rustup component add clippy. It also runs in the project, so the component goes on that toolchain.

With no pin and no default toolchain, rustup cannot choose a toolchain, and the install fails. Then run rustup default stable, or pin a toolchain in rust-toolchain.toml.

The formats: scripts/formats.json

This file names each shared file that a part can go to. A line file, such as .gitignore, needs no entry. Each entry has these keys:

Key What it means
format lines, toml, json, yaml or hooks.
include How the part reaches its own file. extend is the extend key of ruff.toml. extends is the extends list of tsconfig.json and biome.json. pointer is a line in AGENTS.md that names a file.
instead Another name of the same file. A part of biome.json goes to biome.jsonc when only that file exists.
create false when the installer must not make the file. pyproject.toml comes from uv init only.
list and key For YAML: the list that holds the units, and the key that names each item. .pre-commit-config.yaml has repos, named by repo.
comments For a line file: html when the comments are HTML comments, as in AGENTS.md.

In the project

The record: .agents/stack.json

The record has these keys:

Key What it holds Example
version The version of the format. 2
profiles The installed profiles. ["python"]
choices Each role, on or off. {"cx": false, "jagt-protocol": false, "prose": true, "reporter": false, "tasker": true}
tools The installed tools. ["python:lint", "python:test"]
variants The variant of each role that has variants. {"tasker": "git"}
answers The answer of each setup question. A question with an answer is not asked again. The README lists the questions. {"integration": "check", "issues": "top"}
owned_packages The packages that the installer added, keyed by their place in the manifest. A removal takes out only these. For Python the place is profile:group. For TypeScript it is the profile, because npm has no groups. {"python:lint": ["pre-commit", "ruff"]}
generated The hash of index.just and of each <profile>.just that the installer wrote.
started true when the installer wrote the starter Justfile. true
code The globs of the source files of each profile, for @code of the gate. {"python": ["**/*.py"]}
tests The globs of the test files of each profile. test-parent copies only these files into the parent commit. {"python": ["tests/**"]}
steps The steps of just check, in their order. jlog pass reads them. With the answer integration=verify, integration is not in the list. ["tools-check", "release-check", "fmt-check", ...]
programs Each program without install that the project needs, with its check, its expect, its floor in version, and the floor of each owner in owners. The installer writes it at each run. tools-check and just install --check read it, so a clone can check its programs from this key alone. The floors of owners count, and version is the highest of them. A program with install, such as a toolchain, is not in it: it is the state of one machine, and just install sets it up. A program with each_clone, such as the git hooks of a role, is in it, with "each_clone": true. tools-check skips its check in CI. {"just": {"check": "just --version", "version": ">=1.50.0", "owners": {"jnterfaces": ">=1.50.0"}}}
project_programs The programs that the project itself needs. You write it, and the installer keeps it. Each entry has name and check, and can have version, expect and description. The owner is the project. A program without install must be there before a run writes anything. [{"name": "gest", "check": "gest --version", "version": ">=0.6.0"}]
ci The steps that just ci runs after ci-gate. Each one must be a step of just check. You edit it, and just install keeps it. ["test"]
provided_steps The steps that an installed profile or role provides. jlog pass counts a skip only for a step that is not in this list. ["lint", "test", "diff-check"]
justfile_clash The hash of your Justfile and the error of just, when a run took the block out again because the Justfile did not parse with it. While the Justfile keeps this hash, the installer does not add the block.
parts Each unit of each shared file. See below.
parts_version The version of the format of parts. 1
pending_tools, removing_tools, removing_profiles Work that a run that failed did not finish. The next run finishes it.
parts_log_end The id of the last entry of the old log that moved into parts, for a project of an older installer.

The installer keeps any other key that it finds in the record. One old key, added_packages, goes. An entry moves into owned_packages when its tool is a tool of a profile that the run turns on, keeps or turns off. The installer drops the other entries.

The keys of parts are the shared files, and under each file, the units. For example:

"parts": {
  ".gitignore": {
    ".venv": {"state": "added", "needs": ["python"], "holder": "python"}
  },
  "pyproject.toml": {
    "tool.uv.default-groups": {"state": "added", "needs": ["python"], "holder": "python",
                               "value": "all", "made": ["tool", "tool.uv"]}
  },
  "ruff.toml": {
    "extend": {"state": "added", "needs": ["python:lint"], "holder": "python:lint",
               "value": ".agents/config/python/ruff.toml"}
  },
  ".agents/config/python/ruff.toml": {
    "(own file)": {"state": "added", "holder": "python:lint", "needs": ["python:lint"], "hash": "7ca1..."}
  }
}

The name of a unit depends on the format of the file:

Format Unit name Example
lines The line, without a slash at the end. .venv
TOML The dotted key. tool.uv.default-groups
TOML include The include key. extend
JSON include The include list with its value. extends["./.agents/config/typescript/tsconfig.json"]
YAML The list, and the key of the item. repos[repo=https://github.com/astral-sh/ruff-pre-commit]
hooks The event, the group, and the command. hooks.PreToolUse {"matcher": "Bash"} $CLAUDE_PROJECT_DIR/.claude/hooks/raw-git-write-guard.sh

An entry has these fields:

Field What it means
state One of the states below.
needs Each owner that needs the unit.
holder The owner that holds the unit now. When it goes, the next owner in needs holds it.
value The value that the installer wrote, for a unit file.
made What the installer made for the unit, for example the tables tool and tool.uv. They go with the last unit inside them.
file For a file with two names: the file that holds the unit. A part of biome.json has biome.json or biome.jsonc.
hash For an own file, a whole file, a starter or a seed: the hash of what the installer wrote. A starter from an older installer has no hash. Then the file counts as the installer’s while it is as the package ships it now.
earlier Only after a run that stopped: other values that the file can hold for the unit.
unsure Only after a run that stopped and a later run that could not read the file. just install --check fails until a run reads the file.

The states are these:

State Meaning
added The installer added the unit. It goes when no owner needs it.
present The unit was in the file before its owner came. It is yours, and stays.
declined You deleted the unit. The installer does not add it again.
kept The whole file is yours, with no part. You changed a whole config file of an older installer, or you made again a file that you had deleted.
seeded A starter, such as the first AGENTS.md. It is yours from the start.

Some keys of parts are not units. Each one starts with a bracket:

Key What it means
(own file) The file is an own file of an owner.
(whole file) The file is a whole file of a package from before the parts.
(file) The whole file is yours. The installer adds no part to it.
(starter) A role, or the installer, wrote the file from its starter.
(seed) An older installer wrote the file from its seed.

Which file holds a part

A part has one name in the record, the name in profile.json, for example biome.json. The file that holds it can have another name. Biome reads biome.json, else biome.jsonc, and it uses biome.json when both are there.

  • Each entry of the part saves the file that holds it, in file. The installer accepts only biome.json or biome.jsonc there.
  • When only biome.jsonc is there, the part goes to biome.jsonc.
  • When you add a biome.json later, the next run moves the part. It takes the units out of biome.jsonc and adds them to biome.json. A unit that you deleted stays out.
  • just install --check names a part that the next run will move.
  • If one of the two files is a symlink, the installer leaves the part alone. Each run and just install --check say so. The own file that the part includes stays, also after you uninstall its tool.
  • A record of an older installer has no file. The installer then looks for the units in biome.json first, then in biome.jsonc.

The layout of a JSON file

The installer writes each JSON file that it changes as the Biome formatter writes it. So just lint passes on the file. It reads the Biome config of the project to find the layout:

  • The config in biome.json, else in biome.jsonc, with its comments.
  • Each local file that its extends names, from the folder of the file that names it. A local file is a name that starts with ./ or ../, or ends with .json or .jsonc. Any other name is a package, and the installer does not read it.
  • Each entry of overrides whose includes match the file.

It takes these settings, as Biome does:

Setting Default
lineWidth 80
indentStyle tab
indentWidth 2
expand auto
lineEnding lf
json.formatter.trailingCommas none

Each override is a layer after the config, and a later layer wins. In one layer, json.formatter wins over formatter. A project with no Biome config keeps the indent of each file.

The installer does not cover these cases:

  • formatter.useEditorconfig. The installer does not read .editorconfig. Set the layout in the Biome config.
  • trailingCommas set to all with no json.parser.allowTrailingCommas. Biome then asks for a comma after the last item of a .json file, and its parser rejects that comma. The installer writes no such comma, so the file stays valid JSON. tsconfig.json, jsconfig.json and .jsonc files take the comma. biome.json never does.

The package records: .agents/<package>-install.json

The installer writes one record for each package, for example .agents/jnterfaces-install.json. The tasker role uses .agents/gest-git-install.json, the name in the catalog. A profile package gets one too, for example .agents/jnprofile-python-install.json. The main keys are these:

Key What it holds
schema_version The version of the format.
package, source_repository The package and the repository of its clone.
source_revision The commit of the clone that the run installed.
source_version The version of the clone at source_revision: the release tag vX.Y.Z at that commit, the highest when there are several. Else the output of git describe --tags over the release tags, for example v0.1.0-3-g1a2b3c4. Else null.
source_worktree_dirty true when the clone had changes that are not committed. A file that git does not track under .claude/ does not count, because the worktrees of agents are there.
source_requested_commit The commit that the run asked for, if any.
skills, skill_folders The installed skills.
extras The extra files and folders of install_extras.files.
managed_files The hash of each file that the package copied in. A file whose hash is not the recorded hash is yours, and the installer does not overwrite it.
claude_links The links in .claude/skills that the installer made.
merged_hooks, created_settings, seeds For an installer from before the parts.

A run that stops: .agents/stack-pending.json

Before a run writes a shared file, it saves this file:

{"files": {"biome.json": {"old": {...}, "new": {...}}}}

For each file, old is the record before the run and new is the record that the run is writing. "starter": true marks a file that the run writes from a starter. The key is the name of the record, also when the file is biome.jsonc.

When a run stops, the next run reads this file, so it can still take out a part that the stopped run added. A run that works deletes the file. Git ignores it.

The history: .agents/stack-log.jsonl

Each run that changes a file adds one line:

{"kind": "history", "id": "2026-10-31T14:04:22Z-47bb",
 "command": "just install --profile python --defaults",
 "changes": {"ruff.toml": "units", ".gitignore": "lines", "...": "..."},
 "sources": {"jnterfaces": "b4c8b65...", "jnprofile-python": "3a2a1e0..."}}

changes gives the kind of change of each file, which is lines, units, whole or own. sources gives the commit of each package. Nothing reads this file to decide what to do. Git ignores it.

What you can edit

File Can you edit it?
Justfile Yes. It is yours. Put the recipes of the project in it.
CLAUDE.md Yes. It is yours. Keep the line @AGENTS.md, so that Claude Code reads the instructions of the roles.
A shared file, such as .gitignore or ruff.toml Yes. A unit that you change or delete is yours, and the installer keeps your change.
.agents/config/... and .agents/instructions/... No. The installer writes them again. Put your settings in the shared file, for example ruff.toml or AGENTS.md.
.agents/just/... No. A file that you change is yours, and the installer stops changing it. Put your recipes in the Justfile.
.agents/skills/... Only if you want to keep the change. The installer then leaves the file alone and names it.
.agents/stack.json Only the key project_programs, and a Git conflict. Run just install --check after.
.agents/tools_check.py No. jnterfaces installs it, and tools-check runs it.
.agents/*-install.json, .agents/stack-pending.json, .agents/stack-log.jsonl No.

Check the files

The step tools-check is the first step of just check. The installer writes it into .agents/just/index.just. It runs .agents/tools_check.py, which reads the keys programs and project_programs of .agents/stack.json and runs each check. It needs Python 3.9 or later, which uv finds, and it installs and downloads nothing. It runs through jlog, as each recipe line does, so it sees the tools of .jlog/bin.

A Justfile with its own check must run each step of the record, such as tools-check and release-check, because jlog pass reads the steps from the record. A recipe of the project with the name of a step, such as its own release-check, is that step. just check runs it, and it must end with jlog step. The lint of steps names a check that does not, at each run and in just install --check. To check the programs in CI, add tools-check to the list ci. The CI then needs each program of the key programs.

just install --check compares parts in .agents/stack.json with the shared files, and changes nothing. It prints each difference, for example:

  • a unit that is gone, or that you changed
  • a block that lacks its begin or end comment
  • a part that the next run will move
  • a run that stopped

It fails in these cases:

  • A block lacks its begin or end comment.
  • A run stopped, or .agents/stack-pending.json is not a file that the installer wrote.
  • An entry is unsure, because a later run could not read its file.

To finish a run that stopped, run just install again.

just install --dry-run prints each file that a run would change, and writes nothing.
