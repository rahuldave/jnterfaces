How the stack fits together

This guide describes the skill stack on the main branch of jnterfaces. It says where each part lives, what a machine needs, and how an install works. Then it builds a project in layers, from a project with no code to a project with lint, tests and types. Each layer lists the parts that work now and the parts that do not work. The results come from installs into empty Git repositories on 2026-10-29.

On 2026-10-31, a new project of each profile was checked again with code and tests, and just verify passed. The section “Gaps to close” says which gaps a later change closed.

Terms

Term Meaning
skill A folder with a SKILL.md file. An agent reads it to learn one job.
package A Git repository that ships skills, for example nossaifd.
role The name of a job, for example prose. A package does the job, so the package can change and the role name stays.
profile A language setup, for example python. A profile package, such as jnprofile-python, ships it.
tool One unit of the setup of a profile, for example lint. It brings packages, config files and recipes.
manifest The file that lists the dependencies of the project: pyproject.toml, package.json or Cargo.toml.
record A JSON file in .agents/ that lists what the installer wrote, with a hash of each file.
mixin One layer that you add to a project, for example a role or a tool.

Where each part lives

The stack has parts in four places:

Place What it holds
GitHub, rahuldave/... The source of each package: jnterfaces, agent_gest_git_skills, nossaifd, sklanes, and the profile packages jnprofile-python, jnprofile-typescript and jnprofile-rust.
The clone folder One Git clone of each package. The default folder is ~/.local/share/skill-packages.
The project Copies of the skills in .agents/skills, the recipes in .agents/just, the records, and .agents/stack.json.
The machine The programs: git, just, uv, and the programs that some roles need.

The packages and their roles are in this table:

Role Package What it installs Default
none, always installed jnterfaces the just skill, the installer file .agents/install.just always
cx jnterfaces the cx skill no
jagt-protocol jnterfaces the jagt-protocol skill no
prose nossaifd the nossaifd skill, its guide and check.py; the declaude skill, from the declauding skill by Oskar Austegard; the writing flow: an instruction, two hooks and a GitHub workflow yes
tasker agent_gest_git_skills the g* skills, the agent hooks, the starter AGENTS.md yes
reporter sklanes the lanes skill no

Only jnterfaces has an installer, scripts/install_stack.py. The other packages list their files in skill-package.json. The list of packages, roles and profiles is in stack.json of jnterfaces. A profile package also has profile.json, which lists its tools.

The clone folder. The installer looks for each package in the folder that SKILL_PACKAGES_DIR names. If the variable is not set, it looks in the folder that holds the jnterfaces clone that runs. If a clone is missing, the installer clones it from GitHub. Each run prints the folder.

just install finds the jnterfaces clone from two variables. JNTERFACES_DIR names the clone. Otherwise, the clone is in SKILL_PACKAGES_DIR, by default ~/.local/share/skill-packages. The project does not save the folder, so export the variable in your shell profile, for example export SKILL_PACKAGES_DIR=~/Projects. ~/Projects is the folder on the machine that ran the commands of this page. If you set none, just install clones new copies into ~/.local/share/skill-packages.

What a machine needs

A machine needs git 2.40, gh 2.40, just 1.50.0, uv 0.12.13 and jlog 0.2.0, or later versions. The installer, Python, the Python tools and Node all come through uv. jlog is the shell of each recipe in .agents/just, and it logs each line in the run log. When a program is missing, or older than its version floor, the installer stops and writes nothing.

To install the release binary of jlog, run this line. It puts jlog in ~/.local/bin, so put that folder on PATH.

curl -fsSL https://raw.githubusercontent.com/rahuldave/jlog/v0.3.0/scripts/install.sh | sh -s -- --tag v0.3.0

To build jlog from source instead, clone https://github.com/rahuldave/jlog, run git checkout v0.3.0 in the clone, then run just install.

The roles and skills need more programs:

Role or skill Program How the stack handles a missing program
tasker gest 0.6.0, whose gest --version prints (rahuldave) The installer stops. The gest of crates.io does not print (rahuldave), so it fails the check.
tasker jagt 0.6.3 The installer stops. The review packets of the role need it.
cx cx 0.1.0 The installer stops while the skill is on.
jagt-protocol jagt 0.3.0 The installer stops while the skill is on.
reporter node 22 or later The package says to run node with uvx --from 'nodejs-wheel==24.*' node.

Version floors. A floor is the lowest version that an owner of a program accepts, for example >=1.50.0 for just. The installer joins the floors of jnterfaces, the skills, the profiles, the roles and the project, and the highest floor counts. It saves each floor in the key programs of .agents/stack.json, and the step tools-check of just check checks them in each clone. The programs of a profile gives the rules.

The programs of a profile. A profile names the programs that it needs in the key programs of its profile.json. For example, the rust profile needs rustup, the toolchain, which brings cargo, and cargo-llvm-cov. Each program has a check command.

A program that a person must install has a description. For rustup, it gives the address https://rustup.rs/, where a person gets it. A program that the installer can install has an install command, such as cargo +stable install --locked cargo-llvm-cov@0.9.1. In the rust profile, rustup is the only program without an install command. The installer installs the toolchain, the stable toolchain and then cargo-llvm-cov, in that order.

The base of the profile and each tool name the programs that they need. So a tool that is off does not need its programs.

  • A program without an install command. When its check fails, the installer prints the description and stops. It writes nothing. This also stops a run that only removes a tool.
  • A program with an install command. When its check fails, the installer runs the install command, and then the check again. It does this at the end of the run, after the files of the profile, in the folder of the project. So rustup reads the rust-toolchain.toml of the project, if it has one. The rust profile writes no toolchain file, and it keeps the pin of the project. An install with "install_in": "home" runs in the home folder, such as cargo +stable install. If the check fails again, the run stops with an error.
  • A setup of each clone. A program with "each_clone": true, such as the git hooks of the tasker role, is in each clone, not on the machine. A fresh clone does not have it. just install sets it up, and just check fails in a clone without it. In CI, tools-check and just install --check skip it.

The installer runs each command without a shell, and it never downloads a script. It runs each check and install of a program through jlog run, so it sees the PATH that the recipes see. A check installs and downloads nothing.

The installer never uninstalls a program, also when a tool or a profile goes. just install --dry-run lists the missing programs and the installs, and it installs nothing. just install --check lists the missing programs. The programs of a profile gives the keys.

How an install works

The installer runs these steps:

  1. It reads the roles, profiles and tools from the command line and from .agents/stack.json. If neither names a profile, it looks at the files of the project. For example, pyproject.toml turns on the python profile.
  2. It checks each package, and each program of a profile that has no install command. If a check fails, it writes nothing.
  3. It copies the skills and other files of each role and profile into the project, and it writes one record for each package.
  4. It saves the choices in .agents/stack.json.
  5. If the project has no Justfile, it writes the starter Justfile.
  6. If the run adds a tool of a profile and the project has no manifest, it makes one, with uv init --bare, npm init --yes or cargo init --vcs none.
  7. It adds the packages of each tool, with uv add --group or npm install --save-dev. The Rust tools add no crate.
  8. After the package commands succeed, it writes the shared files, such as .gitignore, and the config files of the tools. Shared files and the record tells how.
  9. It writes the recipes of the installed tools in .agents/just. After each step, it saves the record and writes the recipes again.
  10. It checks each program of a profile that has an install command. It installs each missing one, and then checks it again.

A later just install with no names installs the same set again, from the clones as they are. To get the new releases of the packages, run just install --update. It moves the jnterfaces clone to its latest release, by the rules below. Then it moves the clone of each package that the run uses to its latest release. The run uses the profiles, the roles that it installs, and the roles that it removes.

The latest release of a package is the highest release tag vX.Y.Z by semantic version on the default branch of its remote. A tag such as v1.0.0-rc1 or a date is not a release. A commit after the last release is not released, so --update does not install it. The clone keeps its branch, and the branch moves to the commit of the tag. A clone with commits after the latest release moves back to the release, when the remote branch has each of these commits. The record of the package, such as .agents/nossaifd-install.json, gives the tag in source_version.

A package with no release tag gets the newest commit of the remote branch, as a fast-forward. The run prints that the clone has no release tag.

The clones are in SKILL_PACKAGES_DIR, else next to the jnterfaces clone. A --clone NAME=DIR clone is updated too. The installer never discards a local change:

  • A clone with uncommitted changes stops the run. The message names the clone, and the installer writes nothing in the project. An untracked or ignored file where the new commits add a file or a folder stops the run too.
  • A clone that cannot fast-forward stops the run in the same way. A clone cannot fast-forward when its branch and the remote branch each have commits that the other does not have.
  • A clone on a branch that is not the default branch of its remote stays on its branch. The installer prints “Not updated” and the name of the branch, and it does not switch the branch.
  • A clone with its own commits on top of the remote branch stays as it is. The installer prints “Not updated” and keeps the commits.
  • A clone on no branch, or on a branch with no upstream branch, stays as it is. The installer prints “Not updated”. So, to pin a package to a tag or a commit, check out that tag or commit in its clone, for example git -C CLONE checkout v0.4.3. A clone that does not know the default branch of its remote stays as it is too. The message gives the command that sets the default branch.

The installer updates the profile clones first, and then the role clones. A role clone that stops the run does not undo the update of the profile clones.

The installer writes a config file of a tool, for example ruff.toml, when the project has none. It takes the file out with its tool only when nobody changed it.

An edited file stays as you left it. The installer does not overwrite a file of a package that you edited. It names the file, and it installs the other files. The record keeps the hash of the install, so the next run and a removal still see the edit. To get the new version, undo the edit or remove the file. Then run just install again.

A file that no install wrote can be in the place of a file of a package. In that case the install stops, and the installer writes nothing.

The first install. A new project has no Justfile, so it has no just install. Run the installer from the clone for the first install:

uv run ~/Projects/jnterfaces/scripts/install_stack.py --target . prose

A named role asks no questions, so the command turns on prose only. With a named profile or tool and no named role, a terminal asks about each role.

After that, the project has .agents/install.just. A Justfile that has the line import? '.agents/install.just' gets the recipes just install and just uninstall. If the project has a Justfile of its own, the installer adds this line to it, as the next section tells.

The agents. Codex reads skills from .agents/skills. Claude Code reads skills from .claude/skills. So for each installed skill, the installer makes the link .claude/skills/NAME, which points to ../../.agents/skills/NAME. When the skill goes, the link goes. The installer leaves alone any other file or link in .claude/skills, and a .claude or .claude/skills that is a link or a file.

A link that you remove. If you remove a link, no later install makes it again. If you remove the whole .claude/skills folder, the next install makes all the links again.

copier. .agents/install.just defines the variable jn_copier, which runs copier 9 through uvx. copier makes files from a template, and copier update brings in a later version of the template and keeps your edits. So a recipe can use {{jn_copier}} copy TEMPLATE FOLDER with no install.

How the recipes arrive

Each tool of a profile has one recipe file, for example .agents/just/python/lint.just. The profile package installs these files. just install then writes two kinds of file in .agents/just:

  • python.just, a module for each profile. It imports the recipe files of the installed tools only, and its verify runs their checks. Its recipes run in the folder of the project. just python lint runs one. A module has settings of its own, so it sets jlog as its shell.
  • index.just, which .agents/install.just imports. It sets jlog as the shell of the Justfile, with set shell := ["jlog", "sh", "-cu"]. It has a mod line for each profile, and a combined recipe for each recipe name. So just lint runs the lint of each language. Its verify runs the verify of each language, then git diff --check. It also has the steps of just check.

The steps of just check. just check runs these steps in every project:

tools-check release-check ci-gate fmt-check lint typecheck test integration coverage-check docstring-check docs-check prose-check diff-check
  • A combined step ends with the line jlog step NAME, so the run log shows that the step passed.
  • A no-op step is a step that no profile, role or recipe of the Justfile has. Its one line is jlog skip NAME "REASON". In a new project with no language, each step is a no-op step, and just check passes.
  • A step of a profile comes from the installed tools. The python and typescript profiles give lint, typecheck and test. The rust profile gives fmt-check, lint, typecheck, test, coverage-check and docstring-check. coverage-check fails on each changed line of code that no test runs. docstring-check fails on each item with no doc comment.
  • test-paths is a recipe of the python and rust profiles, not a step. It runs only the tests of some test files. The test-parent recipe of the tasker role runs it with the added and changed test files, on the parent commit.
  • diff-check runs git diff --check against the last commit, when the project has a profile.
  • check depends on each step, and its last line is jlog pass.
  • .agents/stack.json lists the steps under steps, and the steps that a profile or a role provides under provided_steps. jlog counts a skip only for a step that is not in provided_steps.

What CI checks. just ci runs ci-gate, then the steps in the list ci of .agents/stack.json:

  • ci-gate comes from a role with a commit gate, such as tasker. It checks that each commit of the pull request passed the gate. It is a step of just check too, so a commit without the trailer stops just check on your machine. Without such a role, ci-gate is a step that logs a skip.
  • The list ci is yours to edit. Run just install after a change. Each name must be a step of just check, so CI never fails on a step that the gate did not see. The installer leaves out any other name, and says so.
  • What to put in it. The gate saw a pass of just check for each commit, so CI need not run it again. Add a step only when a clean machine tells you more than your own, for example a test on Linux. The list is empty at first.
  • No agent runs in CI. An agent costs money on each run and needs a key.

Where the shell is set. just stops with “Setting shell is redefined” when two files of one Justfile set the shell. A test with just 1.50.0 showed this for two imported files too. So the index sets the shell, and .agents/install.just does not. A Justfile that sets its own shell gets an index without the setting. Then the installer asks you to put jlog in front of the shell, for example set shell := ["jlog", "bash", "-c"].

The run ID. The root Justfile has the line export JLOG_RUN := env("JLOG_RUN", uuid()). So all the lines of one just check share one run in the run log, also the lines of the inner just calls. A module or an imported file must not have the line, because it would make a second ID.

How the installer reads the names of the project. It reads names with just --dump. It builds the new files of .agents/just in a stage, a temporary folder in the project that holds a copy of .agents. A copy of the Justfile imports the stage in place of .agents/install.just. The installer runs these steps:

  1. It writes an index with no mod line in the stage. The index has a placeholder recipe for each name of the old index. So a recipe of the Justfile can still depend on check, for example ci: check.
  2. It reads the names of the Justfile from the copy. If the copy does not parse, the installer tries again with the mod lines. If the copy still does not parse, it stops with the error of just.
  3. It reads the names of each role file and each module. A role file must parse alone.
  4. It writes the whole index in the stage without each name of the project. It writes a no-op step only for a step that no role file and no combined recipe has. The copy of the Justfile must parse with it.
  5. Only then does it write each new file over the old file. Each file goes through a file next to it and a rename. So a run that stops leaves each old file whole. When a step fails, the old files stay exactly as they were.

The installer stops, and changes nothing in .agents/just, in these cases:

  • The project defines a name that the index also defines. Examples are a mod rust of the project and the rust profile, or a release recipe of the project and the same recipe in a role file. just would stop with “Module redefined” or “Recipe redefined”. The message names the name, the file of the project that defines it, and the package that defines it too. Remove the local copy, or rename it, then run just install again. just install --dry-run and just install --check name the same conflict.
  • A recipe of a role file has the name of a step of a profile, such as lint. The step of the profile would not run in just check.

When a later edit breaks the Justfile. The index leaves out the names that the Justfile has when you run just install. Three later edits make the Justfile stop parsing:

  • You add set shell to the Justfile. The index sets the shell too.
  • You add a recipe with the name of a recipe of the index, such as lint, and the Justfile does not have set allow-duplicate-recipes.
  • You remove a recipe of the Justfile that a recipe of the index uses. For example, the Justfile has its own lint, so check of the index depends on that lint. When you remove it, just gives the error Recipe `check` has unknown dependency `lint` .

Then just install cannot run, because just cannot read the Justfile, and just install --check fails. Run the installer itself in the folder of the project, the folder with .agents/install.just. It writes the index again for the names that the Justfile has now. The command finds the clone of jnterfaces as .agents/install.just does, and clones it when it is missing. In another folder, the command stops and writes nothing:

jn_dir="${JNTERFACES_DIR:-${SKILL_PACKAGES_DIR:-$HOME/.local/share/skill-packages}/jnterfaces}"
if [ ! -f .agents/install.just ]; then
    echo "Run this in the folder of the project, which has .agents/install.just" >&2; false
elif [ -f "$jn_dir/scripts/install_stack.py" ] || git clone --quiet https://github.com/rahuldave/jnterfaces "$jn_dir"; then
    uv run --script "$jn_dir/scripts/install_stack.py" --target .
fi

The shell that you set must start with jlog, for example set shell := ["jlog", "bash", "-c"]. jlog step, jlog skip and jlog pass work only in a recipe that runs through jlog, so with another shell just check fails.

Commit these files. .agents/install.just imports the index with import?, so a clone without it does not have the recipes, and just gives no error. just install names each file that git does not track, and just install --check fails when one is gone.

A project that jnterfaces started. When the project has no Justfile, the installer writes the starter Justfile, and .agents/stack.json records "started": true. The starter Justfile has set allow-duplicate-recipes. So a recipe in the Justfile itself with the name of a recipe of the index, such as lint, takes its place. It does not take the place of the recipe of a language, so just python verify still runs the lint of the profile. A recipe of yours can also depend on a recipe of the index, for example ci: verify.

A project that jnterfaces did not start has a Justfile of its own. The installer adds one block of lines at the start of that Justfile:

# begin lines of jnterfaces, the installer, from jnterfaces at 1a2b3c4.
# Last written to Justfile by `just install prose`. The record is parts."Justfile" in .agents/stack.json.
import? '.agents/install.just'
export JLOG_RUN := env("JLOG_RUN", uuid())
# end lines of jnterfaces. They stay while the project keeps .agents/stack.json.

The block is a part, as in .gitignore. The installer changes only the block, and your lines stay as they are. The block has no line of JLOG_RUN when the Justfile sets JLOG_RUN itself. The index leaves out each name of the Justfile, so a lint or test of your own stays, and the index gives the other steps.

The installer adds no block in these cases:

  • The Justfile already imports .agents/install.just, with import or import?, in single or double quotes, and sets JLOG_RUN. If the Justfile has the block and a line of yours too, the line goes from the block.
  • The Justfile starts with a #! line, or it is a symlink. Add the lines yourself.
  • The Justfile does not parse before the run. Fix it, then run just install again.
  • You deleted the block. The installer records the lines as declined, and it does not add them again. To have them back, add the lines after the blocks.

A clash with the block. The block imports .agents/install.just, which has the recipes install and uninstall and the variable jn_copier. A recipe of yours with one of these names makes the Justfile fail to parse. Then the installer takes the block out again. It names the clash, and it prints the lines to add by hand.

The record keeps the hash of your Justfile, so the next run does not try again until you change the Justfile.

The lint of steps. A step that hides its lines from the run log can make a gate wrong. just install and just install --check name each step that has one of these:

  • A shebang line or the attribute [script].
  • A line with the prefix -, so just goes on when the line fails.
  • The attribute [no-cd] or [working-directory]. The setting set working-directory that the installer writes into each module is allowed.
  • No jlog step NAME or jlog skip NAME as its last line, or, for check, no jlog pass.

The lint also reads the dependencies of each step. just install --check exits with 1 when the lint finds a step.

The record. .agents/stack.json holds the hash of each file that just install wrote in .agents/just, under generated. The installer changes or removes a file only while its hash is the recorded one. It keeps any other file, and it names that file. Put your own recipes in the Justfile.

With more than one language, a combined recipe gives the same arguments to each language. To give arguments to one language, run just python test x.

Build a project in layers

Each layer adds one mixin. Start at layer 0, and add the layers that the project needs. Each command after layer 1 is a recipe of the project.

For the shortest path to a full project, with each tool and recipe, read Start a Python, TypeScript or Rust project.

Layer 0: an empty Git repository

mkdir notes && cd notes && git init

The project has no code, no manifest and no Justfile.

Layer 1: the writing skills

uv run ~/Projects/jnterfaces/scripts/install_stack.py --target . prose

What you get:

  • .agents/skills/just and .agents/skills/nossaifd, with check.py, and their links in .claude/skills.
  • .agents/skills/declaude and its link in .claude/skills. Oskar Austegard wrote the skill, and he calls it declauding. It is in his repository oaustegard/claude-skills, version 0.14.0, under the MIT licence. nossaifd ships it as declaude, and records each change to its copy in sources/declaude.json.
  • The writing flow of nossaifd, which the nossaifd site describes:
    • an instruction for agents, in .agents/instructions/prose.md, and a line in AGENTS.md that points to it
    • a UserPromptSubmit hook and a Stop hook, in .claude/settings.json and in .codex/hooks.json
    • the workflow .github/workflows/nossaifd-prose.yml, which checks the prose of each pull request. The installer does not write it while the tasker role is on. Layer 2 tells why.
  • CLAUDE.md, with the line @AGENTS.md, when the project has none. Claude Code reads CLAUDE.md and not AGENTS.md, so the line gives it the instruction.
  • .agents/install.just, the records, and .agents/stack.json.
  • The starter Justfile, which imports .agents/install.just. So just install, just uninstall and just install --help work.
  • Two empty lists, .agents/generated.txt and .agents/coverage-exclude.txt, in a project that the installer starts. The lists are yours. The installer never writes them again, and a list that you delete stays deleted.

just prose-check runs the checker on the Markdown pages that changed since the last commit, or on the pages that you name. With no names, it leaves out AGENTS.md and CLAUDE.md, which are instructions for agents. It is the step prose-check of just check:

just prose-check
just prose-check -v README.md

just prose-check runs only the nossaifd checker. The declaude skill has its own scripts, which an agent runs when it revises a draft.

An agent finds the nossaifd and declaude skills by their descriptions, through the links in .claude/skills or the copies in .agents/skills. The instruction in AGENTS.md tells it when to use them.

The nossaifd skill calls the declaude skill at its step 6, after the draft passes the checker. The declaude skill says to run it in an agent that did not write the draft, and not to load it before the draft exists. The declaude skill also has a Stop hook in hooks/hooks.json. The installer does not turn that hook on.

just uninstall prose takes out both skills, the line in AGENTS.md, the instruction file and the two hooks of prose. The hooks of other roles stay. The workflow stays too, because a starter is yours from the start. Delete .github/workflows/nossaifd-prose.yml yourself if you do not want it.

CLAUDE.md also stays. If prose was the only role with a line in AGENTS.md, the installer removes AGENTS.md. Then it says that CLAUDE.md imports a file that is gone, so that you can delete CLAUDE.md.

An install from before nossaifd renamed declauding to declaude has the folder .agents/skills/declauding. just install --update gets the latest release of nossaifd and installs declaude. It also removes the folder declauding and its link, if the installer made them and you did not change or add a file in them.

The installer keeps a file that you edited or added, so the folder stays. For an edited file, it prints “Kept” with its path. When the kept file is SKILL.md, the link stays too, and an agent sees both skills. In both cases the installer prints a line that starts with “Left .agents/skills/declauding”. Then delete .agents/skills/declauding and .claude/skills/declauding yourself. Do the same for a copy that npx installed.

What does not work:

  • A project with a manifest gets a profile. If the project has pyproject.toml or package.json on the first install, the installer finds the profile and adds its default tools. To install the role alone, pass --profile '' on the first install. The record then keeps no profile.

Layer 2: the task tracker

just install tasker

What you get:

  • The g* skills, which track work with Gest.
  • The agent hooks in .claude/hooks and .codex/hooks, with their entries in .claude/settings.json and .codex/hooks.json.
  • A starter AGENTS.md, if the project has none. The starter is yours from then on. just uninstall tasker takes out only the lines of the role, and the rest of the file stays.
  • CLAUDE.md, with the line @AGENTS.md, if the project has none. Layer 1 tells why.

The prose workflow goes. With the tasker role, the gate needs a pass of prose-check for each commit, and CI checks the trailer of the gate. So the workflow .github/workflows/nossaifd-prose.yml of the prose role would check the prose twice:

  • The installer removes the workflow when the installer wrote it and you did not change it.
  • If you changed the workflow, the installer keeps it and says so. Delete it yourself if you do not want it.
  • While the tasker role is on, no install writes the workflow again.
  • just uninstall tasker writes the workflow again, while the prose role is on.
  • If you delete the workflow, it stays deleted.
  • When the prose role is off, the rule does not hold. A workflow that prose left stays.

drop_with in stack.json of jnterfaces holds this rule.

Variants. just install tasker=gitwt works on each task in its own Git worktree, and keeps the main checkout on main. The default, tasker=git, works on a branch in the main checkout. The record saves the variant, and just tasker-mode prints it. The jj variant is not ready yet.

The worktree recipes. In a project that jnterfaces started, the role adds these recipes:

Recipe What it does
just worktree-new NAME [BASE] Makes branch NAME in ../<repo>.worktrees/NAME, sets it up, and runs just setup there
just worktree-sync Sets up a worktree that another tool made, such as Claude Code
just worktrees Lists the worktrees: clean or dirty, merged or not, and the ignored files that a removal deletes
just worktrees-prune Removes the clean, merged worktrees that were idle for 2 hours, with no --force. A worktree with outputs or other ignored files that setup did not put there stays

A worktree has only the files that Git tracks. So setup reads two files in the main checkout. .worktreeinclude has gitignore patterns, and each ignored file that matches is copied, for example .env. .worktreelink has one path on each line, and each path becomes a symbolic link to the main checkout, for example a large data folder. Claude Code and Conductor read .worktreeinclude, and PostHog uses .worktreelink.

Commands in a worktree also make ignored files, such as .venv and test caches. just worktrees-prune keeps a worktree with ignored files, so that it never deletes an output. A third file, .worktreedisposable, has gitignore patterns for the ignored files that a command can make again. Those files do not keep a worktree. Each profile adds its lines to this file, in a block of its own. The Python profile names .venv/ and the caches, the TypeScript profile names node_modules/, and the Rust profile names /target/.

What works. The install, the variant and the worktree recipes work. The session-start hook reports worktrees that are ready to prune, and removes nothing. In gitwt, a git commit in the main checkout gets a warning.

What does not work:

  • The worktree recipes are missing in a project that jnterfaces did not start. There the skills run the script of the gtw skill directly.
  • The skills need gest. gest does not come through uv. The installer prints a warning when it is missing.
  • The starter AGENTS.md has <replace-me> fields. You fill them in.

Layer 3: a language profile

just install --profile python

Use --profile typescript for TypeScript, or --profile rust for Rust. Name a profile once, because the installer saves it.

What you get with python:

  • The package jnprofile-python, with its recipe files and its skill python-profile.
  • pyproject.toml from uv init --bare, with default-groups = "all", so that uv run has the tools.
  • Its lines in .gitignore and .worktreedisposable, in a block of their own at the start of each file.
  • The recipe just setup.
  • The default tools lint and test, which the next layers describe.

What you get with typescript:

  • The package jnprofile-typescript. uv runs npm and node from the nodejs-wheel package.
  • package.json from npm init --yes, and its lines in .gitignore and .worktreedisposable.
  • The default tools lint and typecheck.

What you get with rust:

  • The package jnprofile-rust, with its recipe files and its skill rust-profile. The skill tells an agent which tool gives which recipe, and what each step checks.
  • The Rust rules of the agentic targets review, test-review, docs and prose, in .agents/targets/rust/. jagt render adds them to the packet of each target.
  • Cargo.toml and src/main.rs from cargo init --vcs none.
  • Its lines in .gitignore and .worktreedisposable, such as /target/.
  • The recipes just setup and just build.
  • The default tools lint, typecheck, test and docstring. The tool toml is not a default tool.
  • The programs of each tool. The machine needs rustup first, from https://rustup.rs/.

A profile also turns on its default roles, tasker and prose, but only in a project with no saved roles.

Layer 5: tests

just install test

Python. The tool adds pytest and pytest-cov to the group test. just test and just cov run pytest. With no arguments, a project with no tests yet passes. A selection that runs no test fails.

TypeScript. The tool is on by default. It adds TypeScript, the Node types and c8, which records the lines that the tests run. just test compiles the code into .jnprofile-typescript/build/, and it runs the tests there with node --test under c8. With no .ts file in src yet, it passes. just cov shows the lines that the tests ran.

Rust. The tool installs llvm-tools-preview and cargo-llvm-cov. just test runs the tests with cargo llvm-cov test, and writes the coverage. just coverage-check fails on each changed line of code that no test runs. On the first commit, each line of code must run. just test-paths runs the tests of some files in tests/.

The default tool docstring of Rust gives just docstring-check, which fails on each item with no doc comment.

Layer 6: types

just install typecheck

Python. The tool adds ty to the group lint, and a ty.toml that leaves out .agents, .claude and .codex. just typecheck runs ty check.

TypeScript. The tool adds TypeScript and tsconfig.json. just typecheck runs tsc --noEmit. With no .ts file in src yet, it passes.

Rust. The tool adds no program. just typecheck runs cargo check on the code and the tests.

Layer 7: one check before a commit

just verify runs the checks of each installed tool of each language, then git diff --check, which finds whitespace errors. On a new project with the default tools, just verify passes, for Python and for TypeScript. A Rust project always has code, and just verify passes once each item has a doc comment and the tests run each line. A Rust project gives an example.

How the mixins behave

Add a mixin. just install NAME adds a role, a tool or a profile, and it saves the choice. A tool that fails runs again at the next install.

Remove a mixin. just uninstall NAME takes out a role, a tool or a profile:

  • A role loses its files. Each file that you edited stays.
  • A tool loses the packages that just install added, and its recipes. Each package that the project had before stays. A dependency group that the removal leaves empty goes too. A config file of the tool goes when nobody changed it. The lines of the tool go from the shared files, if no other owner needs them.
  • A profile loses each of its tools, its recipe files and its package. The project keeps pyproject.toml or package.json. If a step fails, the next just install goes on with the removal. A run that names the profile again stops the removal instead. --profile with a list that leaves out a saved profile also turns that profile off.

Shared files and the record

Several owners can add a part to one file. An owner is jnterfaces, a profile such as python, a tool of a profile such as python:lint, or a role such as tasker. Each owner adds its part and takes out only its part. notes/plan-shared-files.md and notes/plan-snippets.md give each decision and its reason. scripts/formats.json lists the shared files that a package can add a part to, with the format of each file. The files of the stack gives each key of the record and of the files that the packages ship.

Three kinds of part. The format of the file sets the kind:

Kind Files What the owner adds
A block of lines .gitignore, .worktreedisposable Its lines, in a block of its own at the start of the file
An include ruff.toml, tsconfig.json, biome.json, AGENTS.md One line or key that reads an own file, which the installer writes under .agents/config/ or .agents/instructions/
Units ty.toml, pyproject.toml, .pre-commit-config.yaml, .claude/settings.json, .codex/hooks.json Keys, items of a list, or hooks

An own file is a file that only the installer writes. Do not edit it. To change a setting, set it in the shared file. Your settings win over the settings of the own file. For example, line-length = 99 in your ruff.toml wins over the line-length = 120 of .agents/config/python/ruff.toml.

A block of lines looks like this:

# begin lines of python:lint, the lint tool of the python profile, from jnprofile-python at c299beb.
# Last written to .gitignore by `just install lint`. The record is parts.".gitignore" in .agents/stack.json.
.ruff_cache/
# end lines of python:lint. `just uninstall lint` removes them.

Your own lines come after the blocks. In a git ignore file, a later line wins, so a line of yours always wins over a line of a block. In AGENTS.md the comments of a block are HTML comments. A TOML key or a YAML item of a part has one comment on the line before it, which names its owner.

The record. The key parts in .agents/stack.json records each unit that the installer added. For each unit, it records the state, the owner that holds the unit, and each owner that needs it. The files are the output of the record. A removal reads the record, never the files, to know what to take out. The states are:

State Meaning
added The installer added the unit. It goes when no owner needs it.
present The unit was in the file before its owner came. It is yours, and stays.
declined You deleted the unit. The installer does not add it again.
kept You changed a whole config file of an older installer. It stays yours, with no part.
seeded A starter, such as the first AGENTS.md. It is yours from the start.

How a part goes.

  • A unit that two owners need stays while either owner is on. When the owner that holds it goes, it passes to the other owner.
  • A unit that you delete stays out. A shared file that you delete stays deleted in the same way, and its own file goes.
  • A unit that you change is yours. It stays when its owners go, and the output names it.
  • Two owners that need one unit with two values stop the run, which names both owners. ruff.toml takes one extend, so it has one owner.
  • A line that you add inside a block moves after the blocks at the next run.
  • When the last part goes and the file holds nothing else, the file goes.

Files that the installer leaves alone. A tsconfig.json or a biome.jsonc with comments is not plain JSON. The installer does not change it, and the output prints the include to add by hand. An extend of your own in ruff.toml stays, and the installer writes no own file. If Git ignores an own file, the run stops, because a fresh clone needs the own file.

A guard. The lint tool of the python profile adds no part to ruff.toml when pyproject.toml has a [tool.ruff] table. An extend there would change your settings and the format of the whole code base. The guard stops a new part only. A part that is there stays when you add [tool.ruff] later.

Roles. A role adds its parts in the same way. The tasker role adds a starter AGENTS.md once. If you delete it while the role is installed, it stays deleted. The role also adds a line to AGENTS.md that points to .agents/instructions/tasker.md. Its hooks are units of .claude/settings.json and .codex/hooks.json.

The line in AGENTS.md is Read and follow @.agents/instructions/tasker.md. Codex reads the path. Claude Code imports the file through AGENTS.md, which it reads through @AGENTS.md in CLAUDE.md.

An older installer wrote the path in backticks, which Claude Code does not import. The next just install changes the line in the block of the role. If you deleted the line, it stays deleted. You must fix two cases by hand:

  • A copy of the old line that you wrote outside the blocks stays. Delete it.
  • If AGENTS.md is a symlink, the installer leaves it alone. Change the line yourself.

The SessionStart hook of the role prints the rules file for Codex, which does not import it. The Claude hook leaves the file out when it is sure that Claude Code imports it, so the rules are not in the context twice. It is sure only of the files that the installer writes:

  • CLAUDE.md at the top of the project holds only the line @AGENTS.md, or is a symlink to AGENTS.md.
  • AGENTS.md is not a symlink. Before the line of the role, it has only blank lines, comments of one line and the lines of other roles.
  • No settings file that the hook can read names claudeMdExcludes. The hook cannot see claude --settings.

In other cases, such as an import in .claude/CLAUDE.md, it prints the file, so the rules can be in the context twice.

Claude Code and Codex show a long hook output only as a preview and a file. So the first line of the output asks the agent to read the whole file.

The log is a history. .agents/stack-log.jsonl gets one entry for each run that changes a file. Nothing reads it to decide what to do. The jnterfaces block of .gitignore names it, so Git does not keep it.

A run that stops. Before a run writes a file, it saves .agents/stack-pending.json with the old and new record of each file. The next run reads it, so it can still take out a part that the stopped run added. Git does not keep this file either.

Branches. When two branches change .agents/stack.json, git gives a conflict in it. Resolve it as for any file. A merge can keep the blocks of both sides and the record of one side. Then the next run takes each block of a known owner into the record.

Check and dry run. just install --check compares the record with the files, prints each difference, and changes nothing. It fails for a block that lacks its begin or end comment, and for a run that stopped. Run just install again to finish such a run. --dry-run prints each file that a run would change.

Projects of an older installer. The first run of this installer moves the record from the old log to parts, once:

  • The lines of the old log become units of the record.
  • A config file that the old installer wrote and that nobody changed becomes an own file and an include.
  • A config file that you changed stays yours, with no include. To have the include, delete the file and run just install again.
  • An AGENTS.md that the old installer wrote and that nobody changed becomes the starter and a pointer. One that you changed stays yours. The hook still prints the rules.
  • The hooks that a role merged become units of the role.
  • The output asks you to run git rm --cached .agents/stack-log.jsonl once.

If an older installer on another branch adds an entry to the log after the move, the run stops. Run the new installer on that branch first. Each person on a project moves to the new installer at the same time.

A package that a profile drops goes, with its Git hook. A package that just install added for a tool, and that no tool in that place lists now, goes at the next just install. An example is pre-commit, which the Python profile once installed for lint. The before_remove of the tool still names it, so the installer first runs uv run --group lint pre-commit uninstall. It runs only when the pre-commit Git hook runs the Python of the project. If the command fails, the removal stops, and the next just install tries it again.

just uninstall lint runs the same command before pre-commit goes.
